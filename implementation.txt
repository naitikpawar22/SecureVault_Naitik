# Project: SecureVault – Secure File Sharing Application

Build a complete, secure, production-minded file-sharing web application named **SecureVault**. Develop the frontend, backend, database, and storage modules separately with clean, maintainable code.

## 1. Technology Stack

* Frontend: React + Vite + Tailwind CSS
* Backend: Node.js + Express.js
* Database: MongoDB Atlas with Mongoose
* File Storage: Private Amazon S3 bucket
* Authentication: JWT, bcrypt, role-based access control
* Encryption: Web Crypto API, AES-256-GCM and ECDH
* File uploads: Streaming and multipart upload support for large files

## 5. Secure File Management

* Upload, list, download, preview, and delete files.
* Support large files using streaming or multipart uploads.
* Encrypt files in the browser before uploading.
* Upload only encrypted file content to the backend/S3.
* Decrypt files in the browser after authorized download.
* Store file metadata and S3 object keys in MongoDB.
* Keep the S3 bucket private and block public access.
* Never create public S3 object URLs.
* Use short-lived, authorized download access where needed.
* Validate file size, file type, ownership, and permissions.

## 6. Encryption and Sharing

* Use AES-256-GCM for file encryption.
* Use ECDH to establish secure key sharing.
* Keep decryption keys out of MongoDB, server logs, and S3.
* Implement secure sharing with Owner and Viewer permissions.
* Allow the owner to revoke access.
* Explain key rotation and re-encryption behavior in the documentation.
* Do not claim that revocation can erase a file or key already downloaded by another user.

## 14. Separate MongoDB Database Schemas

Create a dedicated `server/src/models/` folder. Define each MongoDB collection in its own Mongoose model file. Do not put all schemas in one file.

Create these models:

1. **User.js**

   * `name`
   * `email` (unique, normalized)
   * `passwordHash`
   * `role` (user/admin, with secure defaults)
   * `publicKey` (for encryption key sharing)
   * `mfaEnabled`
   * `createdAt`, `updatedAt`
   * Never store plaintext passwords or private encryption keys.

2. **File.js**

   * `originalName`
   * `ownerId` (reference to User)
   * `s3ObjectKey` (private object key, not a public URL)
   * `encryptedSize`
   * `mimeType`
   * `encryptedFileKey` only if securely wrapped for the owner
   * `encryptionAlgorithm`
   * `iv` and required encryption metadata
   * `status`
   * `createdAt`, `updatedAt`
   * Do not store plaintext file contents or unencrypted file keys.

3. **FilePermission.js**

   * `fileId` (reference to File)
   * `userId` (reference to User)
   * `role` (viewer or owner, as applicable)
   * `wrappedFileKey` (encrypted for the recipient)
   * `grantedBy`
   * `createdAt`
   * Add a unique compound index on `fileId` and `userId`.

4. **AuditLog.js**

   * `fileId`
   * `actorId`
   * `action` (upload, download, share, revoke, delete, etc.)
   * `timestamp`
   * `ipAddress` only when necessary and handled appropriately
   * `metadata` containing safe, non-secret details
   * Never log passwords, JWTs, file contents, or encryption secrets.

5. **RefreshToken.js** (only if refresh tokens are implemented)

   * `userId`
   * `tokenHash`
   * `expiresAt`
   * `revokedAt`
   * Use hashed tokens and expiration cleanup.

## 15. Database Design Requirements

* Keep all schemas in separate files and export each model properly.
* Create a separate database connection module in `server/src/config/db.js`.
* Use MongoDB Atlas and read the connection string from the backend environment configuration.
* Use schema validation, required fields, enums, timestamps, and appropriate indexes.
* Use references between collections where appropriate.
* Add indexes for frequently used queries, including owner, file, user, and audit timestamp.
* Enforce file ownership and permissions in backend services—not only in the frontend.
* Ensure a user cannot access another user's files by changing an ID in the request.
* Use transactions only where supported and needed; handle partial failures safely.
* Add validation for all API inputs and return safe error messages.
* Do not create duplicate models or collections unnecessarily.
* Document the purpose and relationships of every collection in the README.

Before implementing the models, provide a brief database schema overview showing each collection, its fields, references, and indexes. Then implement the models and connect them to the appropriate controllers and services. Ensure the final application uses these schemas consistently.
