# SecureVault: Secure Link Sharing, MFA, Approval Requests, and Version Management

Inspect my existing SecureVault project and implement the following complete workflow. Reuse the current frontend, backend, authentication, database, encryption, file/folder sharing, and audit-log architecture. Do not rewrite unrelated features or create duplicate systems.

## 1. Generate Link

When the file or folder owner clicks **Generate Link**:

* Open a modal to configure the share.
* Allow the owner to select a file or folder.
* Allow an optional expiration date.
* Allow the owner to select the requested access type, such as View Only or Edit, if editing is supported.
* Generate a unique, unguessable link token.
* Save the link settings and owner ID in the database.
* Do not grant access just because someone has the link.
* Show the generated link with a Copy button.
* Keep the file or folder inaccessible to link recipients until the owner approves their request.

## 2. Recipient Opens the Link

When anyone opens the generated link:

### If the visitor is not logged in

* Show the SecureVault Login and Create Account options.
* Allow the visitor to register or log in.
* After registration, require email verification if the existing authentication system supports it.
* Require MFA setup and verification before submitting an access request.

### If the visitor is already logged in

* Require MFA verification if it has not already been completed for the current session or access attempt.
* Do not ask the user to set up MFA again if it is already enabled and verified.

Use authenticator-app TOTP MFA with six-digit codes. Verify MFA on the backend.

Important:

* Successful login and MFA must not automatically grant file access.
* Do not show the file contents, preview, download, or decryption key before approval.
* Do not treat possession of the link as permission.

## 3. Create an Access Request

After the visitor successfully logs in and completes MFA:

* Create an access request for the specific file or folder.
* Store the requester’s user ID, share-link ID, file/folder ID, requested permission, request date, and status.
* Set the initial status to `Pending`.
* Prevent duplicate pending requests from the same account for the same link.
* Show the requester a page saying:

“Your access request has been sent to the owner. You will be notified when the owner responds.”

* Do not allow the requester to approve their own request.

## 4. Notify the Owner

When an access request is created:

* Show a notification to the file or folder owner.
* Add the request to the owner’s **Access Requests** page.
* Display:

  * Requester’s name
  * Requester’s registered email
  * Requested file or folder name
  * Request date and time
  * Requested access type
  * Request status
* Provide **View Request**, **Approve**, and **Reject** actions.
* Ensure only the actual owner or an authorized administrator can manage the request.

## 5. Owner Approves or Rejects

When the owner opens a request:

* Show the requested file/folder details.
* Allow the owner to review the recipient’s identity.
* Allow the owner to choose the final permission:

  * View Only
  * Edit, if supported
  * Download Allowed or Download Blocked
* Allow an optional access expiration date.
* Show an Approve and Reject button.

When the owner clicks **Approve**:

* Verify the owner’s authorization on the backend.
* Update the request status to `Approved`.
* Create or update the recipient’s permission record for that specific file or folder.
* Notify the recipient that access has been approved.
* Allow the recipient to open the file or folder after the backend verifies their permission.

When the owner clicks **Reject**:

* Update the request status to `Rejected`.
* Keep access blocked.
* Notify the recipient.
* Record the action in the audit log.

## 6. Recipient Access After Approval

After approval, the recipient must:

* Sign in using the same account that submitted the request.
* Complete MFA when required.
* Open the same share link.
* Pass backend checks for account identity, approval status, link validity, expiration, and current permissions.

After all checks pass:

### For a file

* Show the file details and authorized preview.
* Allow download only if the owner permitted it.
* Keep the existing client-side decryption design.
* Never expose raw AES keys or private keys to unauthorized users.

### For a folder

* Show the approved folder and only the files/subfolders the recipient is authorized to access.
* Apply permissions to all nested items.
* Prevent access to unrelated files or folders.

If the request is pending, rejected, expired, or revoked, show a clear status message and deny access.

## 7. Version Management

Implement or reuse a **Version History** feature for shared files.

Display:

* Version number
* File name
* Uploaded or updated by
* Date and time
* Version status
* Available actions based on the user’s permission

When a file is updated or replaced:

* Create a new version instead of silently overwriting the existing version.
* Keep earlier versions available to the owner.
* Allow the owner to preview or download a version.
* Allow the owner to restore an earlier version if supported.
* Record version creation and restore actions in the audit log.

For recipients:

* Allow version history access only if the owner’s permissions allow it.
* Do not allow recipients to delete or restore versions unless explicitly permitted.
* Enforce download permissions for every version.
* Keep every version encrypted using the existing SecureVault encryption system.

For folders:

* Show version history for files inside the folder.
* Do not implement folder snapshots unless the existing project already supports them.

## 8. Owner Access Management

Add an owner-side **Manage Access** page for each shared file or folder.

The owner should be able to:

* See all approved recipients.
* See pending requests.
* Change a recipient’s permission.
* Disable download access.
* Revoke a recipient’s access.
* Disable or expire the share link.
* Review access and version history.

When access is revoked:

* Block future access immediately through SecureVault.
* Prevent new previews, downloads, and key retrieval.
* Record the revocation in the audit log.
* Explain that revocation cannot erase copies or decryption keys already downloaded by a recipient.

## 9. Backend Security Requirements

Implement authorization on the backend for every protected endpoint.

Before allowing access, verify:

1. The user is authenticated.
2. The link token is valid and not expired or disabled.
3. The user has completed required MFA.
4. The access request is approved.
5. The user is the approved recipient.
6. The recipient’s permission is still active.
7. The requested action is allowed by that permission.

Additional requirements:

* Do not rely on frontend button hiding for security.
* Prevent users from changing IDs in requests to access another user’s files.
* Do not expose private keys, raw AES file keys, MFA secrets, or recovery codes in API responses or logs.
* Store MFA secrets securely on the backend.
* Add rate limiting to MFA verification and access-request endpoints.
* Use safe error messages and validate all input.
* Keep the existing encryption and secure key-sharing workflow.
* Record link creation, access requests, approval, rejection, permission changes, revocation, file access, and version actions in the audit log.

## 10. UI and Responsive Design

Use the existing SecureVault visual style. Keep the interface simple, professional, accessible, and mobile responsive.

Create or update:

* Generate Link modal
* Login and Create Account pages
* MFA setup and verification page
* Access Request Pending page
* Owner Access Requests page
* Approve/Reject request dialog
* Shared File page
* Shared Folder page
* Manage Access page
* Version History panel
* Notifications

Use clear status badges:
`Pending`, `Approved`, `Rejected`, `Expired`, and `Revoked`.

## 11. Testing

Test all of these cases:

1. A visitor opens a link and creates an account.
2. A registered user logs in and completes MFA.
3. The owner receives the access request.
4. The visitor cannot access the file while the request is pending.
5. The owner approves the request.
6. The approved recipient can access the file or folder.
7. A different account cannot use the approved recipient’s permission.
8. The owner rejects a request and access remains blocked.
9. An expired, disabled, or revoked link cannot provide access.
10. A recipient cannot access files outside the approved folder.
11. Download restrictions apply to current and previous versions.
12. Unauthorized users cannot preview, download, edit, restore, or retrieve file keys.
13. The owner can view version history and restore a version if supported.
14. Audit logs record the relevant actions without exposing secrets.
